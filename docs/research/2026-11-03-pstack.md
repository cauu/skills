# pstack 调研记录

调研时间：2026-11-03。对象：[cursor/plugins/pstack](https://github.com/cursor/plugins/tree/main/pstack)，版本 0.15.36，2026-05-22 至 2026-10-27 共 169 个提交。

本文是 `docs/specs/` 下 S0001–S0009 的共同背景。结论的取舍以 spec 为准。

## 1. pstack 结构

- 入口：`/poteto-mode`。把任务匹配到 23 个 playbook 之一，把步骤原样抄进 todo 列表，按步骤调用其他 skill。
- 约 35 个工具型 skill：理解（how / why / recall / teach）、设计（architect / arena / swarm）、审查（interrogate / blast-radius / no-comments）、验证（create/maintain-verification-skill、benchmark-checklist、create/maintain-formal-verification-skill、statechart）、沉淀（reflect / correct / automate-me）、表达（unslop / technical-writing / sharpen / in-your-own-words）。
- 24 条原则：每条一个文件，poteto-mode 内联索引。
- 按角色指定模型（`/setup-pstack`），多模型交叉审查。依赖 Cursor 特有能力。

## 3. 社区反馈要点

- 收益最高的是 `create-verification-skill`。官方指南：“Of everything in this guide, the verification skill pays off the most”。
- 主要问题是 token 成本（有案例同一任务耗时约翻倍）和人工 review 成为瓶颈。小改动不适用。
- 在 Claude Code 或 Codex 中，子 agent 只能用同一家族模型，多模型对抗效果打折。
- 来源：the-agent-daily.org、codesook.dev、agmazon.com、flaviocopes.com、pstack-claude、open-pstack、ahmedbenaw/pstack。均为二手或作者自述，使用量数字未经核实。

## 4. 已确定的方向（2026-11-03 讨论结论）

1. 不复刻 poteto-mode 路由、playbook 目录和原则库。playbook 的有效部分是“各类改动的证据门槛”，并入 `immutable-spec`（S0002）。
2. 目标：每个 spec 在激活前定好通过标准；agent 自主完成验收，用户只看证据。
   - 通过标准由 `spec-design` 起草、`immutable-spec` 规定格式和激活检查。
   - 自主验收默认依靠 agent 自身能力，证据须来自真实产物。
   - 项目级验收工具 `verification`（S0001）只负责让 agent 能在真实应用上检查，不定义标准。触发时机：① 第一次需要时 create；② 每个 spec 收尾时局部更新；③ 定期全量检查。
3. 工作流：所有工作先建 Task 并认领；spec 统一以 Task-ID 为标识。
   - feature / 优化：immutable-spec → 需求澄清 → 原型决策 → 技术方案 → challenge → 验收标准与验证计划 → 激活执行。
   - bug：先只读复现；无法复现则说明原因并停止；复现后判定复杂度，复杂的建 lite spec，简单的直接修复，证据写入 Task 或 PR。
   - 重构 / 降熵：定期人工触发，参考 pstack Refactoring playbook、`correct`、`no-comments`。
   - 形式化验证：参考 pstack create/maintain-formal-verification-skill。
4. 新增 skill：`verification`、`spec-design`、`bug-fix`、`reduce-entropy`、`formal-verification`。改造：`immutable-spec`（含 orca 版）、`challenge`、`tdd`、`code-review`。

## 5. 设计阶段

pstack 有技术设计阶段（指南 `04-design.md`，“Design before you write code”）：
- `architect`：先用 how/why 摸清系统；arena 并行出至少两个结构不同的方案；先写调用方用法再推类型；design-red-flags 筛选；rationale 模板。
- `arena`：跨模型家族评委选出基础方案，再嫁接其他方案的优点。
- Prototype playbook：用原型回答开放问题。
- 共享代码先写 README。
- multi-phase-plan：设计定下来以后再写计划，每个 PR 以证据收尾。
- “Don't spend adversaries on an abstract plan”：没有代码的计划不值得做对抗审查。

pstack 没有需求阶段，人工关口也是可选的（`architect` 默认不停，要用户说 “with checkpoint”）。

我们的设计阶段由 `spec-design`（S0007）承载：技术方案部分借鉴 architect，需求澄清和两个关口（A 需求确认、B 激活）由我们补充。

| 场景 | pstack | 我们的承载 |

## 7. skill 自身的验收

本仓库交付的是 skill，验收 skill 就是验收 agent 读了它之后会不会照做。采用 `pao-skills` 仓库的方案（Promptfoo，每次新建临时工作区，用确定性断言检查最终输出、文件和 git 状态，用例格式包含 caseId、behavior、regressionRisk、knownOmissions，用例由人审核），被测 agent 换成 Claude（Promptfoo 的 `anthropic:claude-agent-sdk` provider）。用例放在仓库顶层 `evals/<skill>/`，避免被 skills.sh 安装到用户机器上。见 S0008。

## 8. 挑战后的修订（2026-11-03）

- Task-ID 标识从 S0002 拆到 S0009。
- 删除 `Change-Type: formal`，形式化检查改为一种验证方式。
- optimization 门槛放宽为“基线 + 改后数据 + 测量方法”。
- 证据行必须摘录关键输出。
- `immutable-spec-orca` 声明依赖 `immutable-spec`；`bug-fix`、`reduce-entropy`、`spec-design` 内联自己需要的门槛，由一致性检查保证一致。
